---
topic: Slide Artifact Model: rearchitect the slide plan from flat SlideKind types into template-based Artifacts with placeholder resolution
updated: 2026-07-31T23:16
---

- (direction) User wants to replace flat SlideKind taxonomy (text, divider, song-title, song-lyric, scripture, sermon, closing-prayer, family, image, body) with a template-based Artifact model where each rundown entry is an Artifact with a visual template, placeholders for dynamic content, and optional auto-inserted children (song lyrics).
- (direction) Each Artifact is a visual template (like a reusable slide layout). Fixed Artifacts have hardcoded content (e.g., Bible Verse Contemplation = John 4:23). Dynamic Artifacts resolve placeholders from form input (e.g., Verse Reading fills reference+text from form). Song-title and song-lyric are auto-inserted children based on hymn number from form.
- (direction) Sermon flyer is a special Artifact type: full-bleed uploaded image from form. Family & Youth (Slide 56) is a composite Artifact: 2 photos + structured text with artistic layout. User acknowledges this is tricky and has a specific reference layout.
- (direction) User envisions a future canvas editor (like Canva) for editing Artifacts visually online with WYSIWYG output. This is out of scope for this spec but shapes the architecture: Artifacts must be defined in a way that could later be rendered/edited on a canvas.
- (decision) CAP-1: Artifact Registry — a declarative catalog of all worship slide templates (Welcome, Bible Talk Sequence, Prayer Partners, Opening Song, Verse Reading, Bible Verse Contemplation, Sermon, Family & Youth, etc.) with their layout rules, placeholder schema, and content resolution strategy.
- (decision) CAP-2: Artifact-based Slide Plan — buildSlidePlan outputs Artifact instances (not flat SlideKind items) where each rundown entry maps to one Artifact, and songs expand into child slides automatically.
- (decision) CAP-3: Live Slide Preview uses Artifact types in the badge column (instead of raw SlideKind), with Artifact grouping visible in the rundown table.
- (decision) CAP-4: Unified rendering — each Artifact type carries enough information to render to PPTX (pptxgenjs), web SlideView (React), and web preview (list row) through a single source of truth. The Artifact definition encodes layout rules, not the renderer.
- (constraint) buildSlidePlan remains the single slide planner consumed by PPTX, web slideshow, and presenter mode. The Artifact model is a rearchitecture of what buildSlidePlan outputs, not a new parallel system.
- (constraint) The rundown order is the service order. The Artifact sequence must match the existing slide sequence produced by buildSlidePlan today. No slide reordering in this spec.
- (decision) Canvas editor IS in scope. Purpose: allow a human to edit template layouts visually (one-time design changes), not weekly content. Few layers per slide, so WYSIWYG is achievable. This resolves Q1: layout stored as positioned-element JSON (x,y,w,h,fontSize,color) editable via canvas, rendered to both web and PPTX from the same data.
- (decision) Refined Artifact taxonomy to 7 base types: (1) General — canvas-editable, no weekly placeholders; (2) TextPlaceholder — canvas-editable + text slots that change weekly; (3) FullScreenImage — single full-bleed image placeholder, changes weekly; (4) ImagePlaceholder — canvas-editable + image placeholder slots, changes weekly; (5) MixPlaceholder — canvas-editable + image + text placeholders, changes weekly; (6) SongSet — auto-generated title + lyric slides; (7) Announcement — list-driven full-screen images.
- (decision) Q2 resolved: Family & Youth = MixPlaceholder (single artifact with image + text placeholders). Q3 resolved: Registry must be runtime-mutable (JSON-persisted) since canvas editor saves layout changes. Compile-time TypeScript constants replaced by JSON template definitions loaded at runtime.
- (decision) Dynamic Artifacts (like TextPlaceholder) can have standing default content embedded in the template (e.g. default Bible verses), behaving like a General slide if not overridden by the user form.
- (decision) Aligned artifact-catalog.md notes with PPTX extracted JSON data (SSOT) to serve as initial content baseline.
- (decision) Q1 Resolved: Canvas editor will be built with Fabric.js. It natively supports layering (z-index) which fits the use case.
- (decision) Adopted architecture spine (architecture-epic-16) as a companion to ensure downstream builders follow the defined invariants (SQLite registry, Fat Payload AST, Fabric.js Uncontrolled Wrapper).
- (decision) Confirmed Uncontrolled Wrapper architecture (manual save) is acceptable over auto-save to prioritize canvas performance.
- (decision) CAP-9 added: Implement strict server-side schema validation (e.g., Zod) on the Canvas JSON output to prevent SSRF and ensure required placeholders cannot be deleted or bypassed.
- (direction) User approved the complete Epic 16 / Story 16.1 default decision package on 2026-07-23 and requested bmad-spec followed by spek-to-coding.
- (decision) SQLite is the live Artifact Registry SSOT; data/default-registry.json is a startup seed that inserts missing template IDs only and never overwrites persisted administrator edits.
- (decision) Artifact templates are global across services; only a DB-revalidated admin may access the editor or registry management APIs, while later server-side planners and renderers read the registry internally.
- (decision) Story 16.1 includes registry persistence, seed behavior, strict validation, admin APIs, and the minimal canvas editor; buildSlidePlan migration, unified renderers, and semantic preview remain Stories 16.2 through 16.4.
- (decision) The admin editor route is /admin/artifacts; management APIs are /api/admin/artifacts, /api/admin/artifacts/[id], and /api/admin/artifacts/[id]/reset, all guarded by requireAdminSession.
- (decision) The Story 16.1 editor modifies existing seeded templates only: select, move, resize, edit fixed text/font/color, save, reload, and reset one template; it cannot create/delete templates or elements, and required elements cannot be removed.
- (decision) Fabric.js owns uncontrolled 16:9 canvas state; persisted coordinates use normalized 0-100 values and React reads serialized state only on explicit Save.
- (decision) BibleVerseContemplation is always TextPlaceholder with standing default reference/text values rather than changing base type at runtime.
- (decision) SongSet, FullScreenImage, and Announcement layouts remain registry-defined but are read-only in the Story 16.1 canvas; SongSet supplies separate title and lyric layout variants.
- (decision) Registry image references accept only valid local upload references, bundled public asset paths, or HTTP(S) URLs accepted by the existing image safety policy; unsafe and arbitrary references are rejected server-side.
- (decision) Reset restores one template from its shipped seed without touching other templates; required seed entries remain recoverable.
- (assumption) Registry writes use updatedAt optimistic concurrency and return HTTP 409 for stale saves or resets, following the repository existing stale-write safety pattern.
- (constraint) Story 16.1 must not change SlidePlanItem, SlideKind, buildSlidePlan output, slide order, PPTX rendering, web SlideView rendering, or preview badges; existing slide-plan behavior remains the regression baseline.
- (decision) The committed data/default-registry.json is the v0 extraction baseline, not the final v1 contract; Story 16.1 transforms it while preserving geometry and content evidence from data/raw-slides.json and slides-new reference images.
- (decision) Normalized coordinates are percentage units relative to the 16:9 canvas, but elements may extend beyond 0..100 to preserve intentional off-canvas clipping from the source deck; widths and heights remain positive and all values finite.
- (constraint) Every bundled asset reference in the shipped v1 seed must resolve to a committed runtime asset; the local untracked source PPTX may be used for extraction but must not be required at runtime, in tests, or by another host.
- (note) Preservation audit found the v0 seed has 25 templates, only five represented base types, separate song-title/song-lyric entries, off-canvas geometry, BibleVerseContemplation typed general, and references to absent public/assets files; Story 16.1 explicitly normalizes these gaps.
- (note) Wrapper-only content dropped from the product contract: BMad invocation ceremony, host transition mechanics, and chat wording remain operational workflow metadata rather than product requirements.
