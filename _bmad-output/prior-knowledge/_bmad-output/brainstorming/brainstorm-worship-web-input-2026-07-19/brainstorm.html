Teknik 1

Role Playing — Suara Setiap Stakeholder

🎵
Pak Tua:
Saya biasanya terima rundown ibadah lewat WhatsApp. Kalau bisa saya ketik langsung di web — tanggal, siapa yang khotbah, lagu SDAH nomor berapa — itu sudah cukup. Jangan yang ribet-ribet. Saya harus bisa selesai sebelum rapat selesai.
📱
Dian:
Yang paling sering bikin saya panik itu kalau data masuk telat dari Telegram. Kadang Sabtu pagi baru ada. Kalau ada web form, saya sendiri bisa input dari informasi rapat tanpa tunggu siapapun kirim ke bot. Minimal saya butuh: tanggal, 3-4 lagu, ayat tema, khotbah siapa judulnya apa.
💻
Naya:
Kalau saya lihat user Pak Tua dan Dian — mereka butuh structured form, bukan textarea markdown. Individual field per elemen ibadah. Tapi harus ada hymn picker dengan autocomplete — ketik nomor "320" langsung muncul judul "Rejoice, Ye Pure in Heart". Dan jumlah lagu jangan di-fix 4 slot, harus dinamis.
🔧
Galih:
Berita baiknya: POST /api/services sudah ada, coerceStructuredFields sudah handle patch per field, dan tabel hymns sudah berisi 695 lagu SDAH. Kita cuma perlu UI form yang output ParsedRundown JSON — backendnya sudah 80% siap. Yang perlu kita putuskan: tulis langsung ke parsed_data, atau generate raw_payload terus re-parse?
🎵
Pak Tua:
Saya juga mau bisa copy dari minggu lalu. Banyak elemen yang sama — cuma ganti pembicara dan lagu. Jangan harus isi dari nol setiap kali.
📱
Dian:
Dan preview! Saya mau lihat seperti apa slide-nya sebelum disimpan. Kalau ada yang salah — nama salah, ayat salah — saya bisa langsung edit tanpa harus generate PPTX dulu baru tahu salah.
Teknik 2

Morphological Analysis — Parameter × Opsi

🔧
Galih:
Saya petakan parameter-parameternya. Data Model: tiga opsi — tulis langsung ke parsed_data, generate raw_payload lalu re-parse, atau bikin staging table baru. Hymn Input: nomor-only, title-search autocomplete, browse modal, atau comma-separated bulk. Concurrency: pakai optimistic locking yang sudah ada (updated_at 409), pessimistic lock, atau last-write-wins.
💻
Naya:
Dari sisi UX, saya vote: tulis langsung ke parsed_data (paling sederhana, skip parser overhead), title-search autocomplete (operator kadang ingat judul tapi lupa nomor), real-time field-level validation (feedback langsung), dan dedicated page bukan modal. Modal terlalu sempit untuk form sebanyak ini.
📱
Dian:
Untuk auth scope — cukup operator + admin. Semua yang bisa login sekarang sudah punya salah satu dari dua role itu. Jangan bikin role baru, tambah complexity doang. Dan preview-nya pakai slide-plan rendering yang sama — saya mau lihat persis apa yang akan tampil di projector.
🔧
Galih:
Kalau begitu kombo terbaiknya: web-form → parsed_data langsung → autocomplete hymn by number+title → real-time validation → operator/admin role → dedicated /services/new page → optimistic locking (existing pattern) → slide-plan preview. Semua ini maximize reuse dari yang sudah ada.
Teknik 3

Disney Method — Dreamer → Realist → Critic

🎵
Pak Tua:
*memasuki Dreamer room* — Bayangkan kalau saya buka web, klik "New Service", pilih tanggal, dan sistem sudah tahu ini Sabbath ke berapa dalam bulan ini. Otomatis suggest template yang biasa dipakai. Saya tinggal ganti nama pembicara dan nomor lagu. One-click clone dari minggu lalu — auto-increment tanggal, langsung edit yang berubah saja.
💻
Naya:
*di Dreamer room juga* — Full liturgy builder! Drag-drop setiap elemen ibadah, visual timeline dari pembukaan sampai penutup. Hymn picker yang bisa play audio preview. Scripture input yang langsung render ayat KJV inline. Mobile-first supaya bisa isi di HP saat rapat.
🔧
Galih:
*pindah ke Realist room* — Oke, ground truth. POST /api/services sudah ada — kita extend supaya terima structured JSON body, bukan cuma raw text. Tambahkan source field ("web" vs "telegram"). Buat WorshipForm component di /services/new dengan: date picker, dynamic hymn inputs, themeVerse, verseReading, sermon (speaker+title), specialSong, closingPrayer, familyYouth. Form generates ParsedRundown client-side, POST to API.
📱
Dian:
*masuk Critic room* — Wait. Kalau operator bikin service untuk tanggal yang sudah ada dari Telegram — kita dapat duplikat. Harus ada date collision check. Dan jangan generate synthetic raw_payload — itu fragile. Parser bisa berubah, roundtrip pecah. Tulis langsung ke parsed_data, kasih raw_payload yang jujur: "Created via web form".
🔧
Galih:
*masih di Critic room* — Setuju soal raw_payload. Dan satu lagi: hymn slot count bukan fixed. Ada ibadah 3 lagu, ada yang 5. Form harus dynamic list — "Add Hymn" button, bisa hapus per item. Dan optimistic concurrency: kalau Dian dan Pak Tua edit bersamaan, yang submit belakangan harus dapat warning 409, bukan silent overwrite.
Teknik 4

Build on What Works — Amplify Existing Patterns

🔧
Galih:
Saya audit codebase kita. Yang sudah jalan dan bisa di-leverage: coerceStructuredFields + applyStructuredFields untuk PUT path — web form tinggal kirim field patches, backend apply ke existing parsed_data. POST /api/services sudah terima parsed_data. Tabel hymns sudah ada 695 entries. updated_at optimistic locking sudah enforced. Backend-nya 80% ready.
💻
Naya:
Dari UI side: EditForm sudah punya textarea + parse preview. Kita bisa extend dengan toggle: raw mode vs structured mode. Operator yang terbiasa bisa tetap pakai textarea, yang baru bisa pakai form fields. Dan AnnouncementsManager sudah punya drag-drop upload — bisa di-link dari worship form sebagai optional step.
📱
Dian:
Preview component yang sudah ada di service detail page — reuse itu di form create juga. Saya mau lihat rundown lengkap sebelum save. Dan yang paling penting: /services/new belum ada — ini clean slate, kita bisa design dari nol tapi tetap match aesthetic yang sudah ada.
🎵
Pak Tua:
Webhook sudah punya upsert by date kan? Pakai logic yang sama — kalau operator create service untuk tanggal yang sudah ada, tampilkan peringatan: "Service untuk tanggal ini sudah ada. Mau edit yang existing?" Jangan diam-diam bikin duplikat.

✨ Sintesis — Yang Kami Putuskan

🧩 Gap Sebenarnya: Backend sudah 80% ready. Yang kurang hanya frontend form yang berbicara dalam bahasa ParsedRundown yang sama dengan output Telegram/webhook.
📐 Arsitektur: Structured form di /services/new (create) + enhanced EditForm di /services/[id] (edit) dengan toggle raw/structured mode. Form produce ParsedRundown JSON langsung — tidak perlu synthetic raw_payload.
🎶 Hymn Input: Dynamic list (bukan fixed slots) dengan autocomplete — cari by nomor SDAH atau judul. Tampilkan first line sebagai konfirmasi. "Add Hymn" / "Remove" per item.
📅 Date Collision: Check existing service by date saat create. Jika sudah ada — tawarkan edit yang existing, bukan silent duplicate.
🔄 Backend Minimal: POST /api/services sudah ada — extend untuk terima structured body dengan source: "web". PUT path sudah support field patches via coerceStructuredFields.
👁️ Preview: Reuse slide-plan rendering component — operator lihat persis apa yang akan tampil di projector sebelum save.
🔒 Concurrency: Honor existing optimistic locking (updated_at 409). Web form fetch updated_at on load, kirim balik on save, handle 409 dengan prompt refresh.
🎯 Arah Terpilih: Structured form at /services/new, enhanced EditForm with field mode toggle, same ParsedRundown shape as webhook output. Web-created services set raw_payload to honest "Created via web form" marker. Downstream (slide-plan, PPTX, presenter) tetap untouched.
